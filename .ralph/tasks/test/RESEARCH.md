# Research: Demo Project for Manual Testing

## Task Summary

Create a demo project in `examples/` folder to manually test the dcache CLI as an npm package.

## Current State

### Project Structure

```

libs/cli/             # CLI commands: run (glob/nx mode), clear, help
libs/config/          # Config loading, logger, lock-file detection
libs/hasher/          # File hashing (SHA256, streaming)

libs/runner/          # Task execution via child_process spawn

```

### CLI Commands Available

From `libs/cli/src/index.ts`:

```
dcache run <command> --glob <pattern>    # Run with glob mode (working)
dcache run <task> --project <name>       # Nx mode (NOT implemented)
dcache clear                             # Clear the cache
dcache --help                            # Show help
```

### How the CLI Works (`libs/cli/src/commands/run.ts`)

1. `loadConfig()` — reads `dcache.config.json` (optional) + env vars
2. `findLockFile(cwd)` — searches for bun.lockb, package-lock.json, etc.
3. `FilesystemCacheProvider(config.cacheDir)` — default: `node_modules/.cache/dcache`
4. `fg(glob, { absolute: true })` — resolves source files via fast-glob
5. `computeHash({ files, lockFilePath, taskManifest })` — SHA256 of files + lock + task config
6. Cache check: if hit, replay stdout/stderr; if miss, run task and cache result
7. `runTask(cmd, args)` — spawns child process, captures output + exit code + duration

### Package Resolution — Critical Finding

- All `@dcache/*` imports use **tsconfig path aliases** (`tsconfig.base.json`), NOT npm packages
- There are **no `@dcache/*` symlinks in `node_modules/`** — bun resolves them via tsconfig paths
- The compiled dist output (`dist/`) still contains unresolved `@dcache/*` imports — it is NOT self-contained
- **`bun run apps/dcache/src/main.ts`** works from monorepo root (bun reads tsconfig paths)
- The `apps/dcache/package.json` has `"bin": { "dcache": "./src/main.ts" }` pointing to TS source

## Approach for Demo Project

### Strategy: Add `examples/*` to bun workspaces

Since the package uses tsconfig path aliases (not npm packages), the demo project should live within the monorepo's workspace resolution. Adding `examples/*` to the root `workspaces` array lets bun resolve `@dcache/cli` (and transitively all `@dcache/*` libs) via the workspace.

### What the Demo Needs

1. **`examples/basic/`** — a simple project with source files that dcache can cache
2. **Some source files** — e.g., a few `.ts` files so the glob pattern has targets
3. **A `package.json`** — with scripts that invoke dcache commands
4. **A lock file** — `bun.lockb` or similar (will be generated by `bun install`)

### Demo Scenarios to Test

1. **Cache miss** — first run of `dcache run "echo hello" --glob "src/**/*.ts"`
2. **Cache hit** — second run of same command (should replay from cache)
3. **Cache invalidation** — modify a source file, run again (should be a miss)
4. **Clear cache** — `dcache clear`
5. **Help** — `dcache --help`

### How to Invoke dcache from the Demo

Option A (recommended): Use `bun run` with the dcache entry point:
```json
{
  "scripts": {
    "cache:run": "bun run ../../apps/dcache/src/main.ts run",
    "cache:clear": "bun run ../../apps/dcache/src/main.ts clear"
  }
}
```

Option B: Add `@dcache/dcache` as a workspace dependency and use the bin:
```json
{
  "dependencies": {
    "@dcache/dcache": "workspace:*"
  }
}
```
Then `bunx dcache run ...` — but this depends on bun resolving the TS bin correctly.

Option C: Use a shell script wrapper.

**Recommendation**: Option A is simplest and most reliable. Option B is more realistic for an "npm package" test but requires bun to resolve TS bin entries.

## Ordering Constraints

1. Root `package.json` must be updated before `bun install` can resolve workspace deps
2. `bun install` must run after adding `examples/*` to workspaces
3. Build is NOT required — bun runs TS source directly
4. Demo scripts should be tested in sequence: help → run (miss) → run (hit) → modify → run (miss) → clear

## Edge Cases

- The `dcache run` glob mode splits the command on whitespace (`parsed.taskCommand.split(/\s+/)`) — commands with spaces in args need care
- `findLockFile` searches cwd upward — from `examples/basic/` it will find root `bun.lock`
- Default cache dir is `node_modules/.cache/dcache` relative to cwd — will be `examples/basic/node_modules/.cache/dcache`
- The demo project will NOT have its own `node_modules` unless it has dependencies — default cache dir is `node_modules/.cache/dcache`. However, `FilesystemCacheProvider.set()` uses `mkdir({ recursive: true })` so the dir is auto-created on first cache write. No issue here.
- `loadConfig()` resolves `cwd` to `process.cwd()` — so running from `examples/basic/` will look for `dcache.config.json` there and default cache dir to `examples/basic/node_modules/.cache/dcache`.
- Consider using a `dcache.config.json` in the example with `"cacheDir": ".dcache"` for visibility (so users can inspect cache contents easily).
